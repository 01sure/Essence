# ServSales AI 业务闭环

## 1. 服务对象

| 角色     | 目标                                            | 使用系统的方式                   |
| -------- | ----------------------------------------------- | -------------------------------- |
| 消费者   | 快速选到合适的智能穿戴产品，并解决订单/售后问题 | 商城商品页聊天组件               |
| 一线客服 | 接管 AI 无法闭环的问题，减少重复询问            | 坐席工作台、会话上下文、售后工单 |
| 客服主管 | 控制服务质量和处理效率                          | 会话池、质检、工单和经营看板     |
| 运营人员 | 让商品、活动和政策内容及时生效                  | 商品库、知识库、话术配置         |

消费者是被服务对象，客服是业务执行者，主管和运营是管理者。系统不把“管理员”当成单一用户角色。

## 2. 业务边界

系统负责：

- 商品咨询、场景推荐和商品卡片点击追踪；
- 订单状态查询和物流信息解释；
- 售后诉求收集、工单分派、处理状态和解决结果；
- 复杂问题转人工，并将完整会话上下文交给坐席；
- 质检和运营指标分析。

系统不负责：

- 实际支付、退款和发货执行；
- 修改商城订单的最终状态；
- 取代人工客服处理高风险投诉。

订单、支付、库存和物流属于外部商城系统，当前通过适配器/模拟数据接入。售后工单是本系统负责的协同对象。

## 3. 核心闭环

```text
商品页咨询
  -> AI 识别场景并检索商品/政策
  -> 推荐商品并记录点击行为
  -> 订单/物流查询
  -> 无法解决时转人工
  -> 创建售后工单并分配坐席
  -> 处理、解决、关闭
  -> 评价与质检
  -> 主管根据转人工原因和工单类别优化知识库
```

## 4. 关键业务指标

- AI 独立解决率：未转人工会话 / 总会话；
- 商品推荐点击率：点击商品的会话 / 展示商品推荐的会话；
- 人工首次响应时长：进入人工池到首次人工回复的时间；
- 售后一次解决率：无需重复开单且进入 resolved 的工单 / 已解决工单；
- 工单积压量：open 与 processing 状态工单数量；
- 质检平均分：主管完成质检的会话平均得分。

## 5. 工程约束

- LLM、Embedding、Elasticsearch 都是可替换基础设施，业务流程不能直接依赖具体厂商；
- 外部订单系统通过适配器接入，AI 只能解释查询结果，不能编造订单状态；
- 工单状态变化必须留下事件，便于审计和看板统计；
- 生产环境禁止默认密钥和通配 CORS；健康检查必须反映关键依赖是否降级；
- 单元测试使用 Mock LLM，真实模型只用于少量联调测试。
